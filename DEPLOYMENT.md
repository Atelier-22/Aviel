# Deployment

Four pieces, three places:

| Piece | Goes to | What it is |
| --- | --- | --- |
| [`astraeya-api/`](astraeya-api/) | **Render** — web service + Postgres | Express API. Owns the database, auth, and every call to Claude |
| [`astraeya-voice/`](astraeya-voice/) | **Render** — private service | Python voice server (Kokoro + Piper). Only the API can reach it |
| [`astraeya-web/`](astraeya-web/) | **Vercel** | Next.js frontend. No database, no API keys — it calls the Render API |
| [`astraeya-mobile/`](astraeya-mobile/) | Expo / EAS | React Native app. Calls the same Render API |

The frontend holds no secrets and talks to nothing but the API. The API is the
only thing that touches Postgres or the Anthropic key.

---

## Order matters

Deploy the **backend first**. The frontend needs the API's URL as a build-time
variable, and the API needs the frontend's URL for CORS — so there is one
chicken-and-egg step, handled in step 3 below.

---

## 1. Render — API + database

The repo has a [`render.yaml`](render.yaml) blueprint, so Render can create
both resources itself.

1. [render.com](https://render.com) → **New** → **Blueprint**
2. Connect the `astraeya` repo. Render reads `render.yaml` and shows a web service
   (`astraeya-api`) plus a Postgres database (`astraeya-db`)
3. It will prompt for the two values marked `sync: false`:

   | Variable | Value |
   | --- | --- |
   | `ANTHROPIC_API_KEY` | your key from [console.anthropic.com](https://console.anthropic.com/) |
   | `CORS_ORIGINS` | leave as `http://localhost:3000` for now — corrected in step 3 |

   `DATABASE_URL` is wired to the database automatically and `JWT_SECRET` is
   generated by Render. You do not set either by hand.

4. Click apply. First build takes a few minutes.

**No manual database setup is needed.** The service applies its own migrations
at boot from [`astraeya-api/drizzle/`](astraeya-api/drizzle/) — a fresh database
provisions itself on first start. If migrations fail the process exits rather
than serving requests against a half-built schema, so a red deploy means read
the logs, don't retry blindly.

When it goes green, check it:

```bash
curl https://astraeya-api.onrender.com/health
# {"status":"ok","aiProvider":"configured"}
```

If `aiProvider` says `not_configured`, the Anthropic key didn't take — chat
will return a 503 with that same explanation rather than a fake reply.

### Creating the service by hand instead

If the database already exists, the blueprint will collide with it on name — set
the service up manually instead (**New → Web Service**):

| Field | Value |
| --- | --- |
| Root Directory | `astraeya-api` |
| Region | same as the database |
| Build Command | `npm ci --include=dev && npm run build` |
| Start Command | `npm start` |
| Health Check Path | `/health` |

Two failure modes, both with unhelpful error messages:

- **Root Directory left blank** → `ENOENT: no such file or directory, open
  '/opt/render/project/src/package.json'`. Render is looking at the repo root;
  this is a monorepo and the service lives in a subfolder.
- **`--include=dev` omitted** → `error TS5108: Option 'moduleResolution=node10'
  has been removed`, or `tsc: not found`. Setting `NODE_ENV=production` makes
  npm skip devDependencies, and TypeScript is a devDependency — so the build
  runs with no compiler installed and picks up whatever `tsc` it can find, which
  may be a different major version than the lockfile pins.

> **Free tier, two catches.** Render's free web services sleep after 15 minutes
> idle, so the first request after a quiet spell takes ~30 seconds to wake. And
> free Postgres is deleted after 30 days. Both are fine for testing; neither is
> fine for real users.

Copy the service URL — something like `https://astraeya-api.onrender.com`.

## 2. Vercel — frontend

1. [vercel.com](https://vercel.com) → **Add New** → **Project** → import `astraeya`
2. **Root Directory: `astraeya-web`** — this is the one setting that matters. It's a
   monorepo; Vercel has to be told which folder holds the Next.js app
3. Environment variables:

   | Name | Value |
   | --- | --- |
   | `NEXT_PUBLIC_API_URL` | your Render URL, no trailing slash |
   | `NEXTAUTH_SECRET` | generate: `openssl rand -base64 32` |
   | `NEXTAUTH_URL` | your Vercel URL, e.g. `https://astraeya.vercel.app` |

   `NEXT_PUBLIC_API_URL` is compiled into the browser bundle, so it must be set
   **before** the build. Changing it later requires a redeploy, not just a
   restart.

   `NEXTAUTH_SECRET` is unrelated to the backend's `JWT_SECRET` — one encrypts
   the browser's session cookie, the other signs API tokens. They are different
   values with different jobs.

4. Deploy.

## 3. Close the loop

Back in Render → `astraeya-api` → **Environment**, set `CORS_ORIGINS` to your real
Vercel URL:

```
CORS_ORIGINS=https://astraeya.vercel.app
```

Save; Render restarts the service. Preview deployments on `*.vercel.app` are
allowed automatically, so branch previews work without touching this again.

Then register an account on your Vercel URL and send a message. That exercises
the whole chain: browser → Vercel → Render → Postgres → Claude and back.

## 4. Expo — mobile

Point the app at the same API and build:

```bash
cd astraeya-mobile
EXPO_PUBLIC_API_URL=https://astraeya-api.onrender.com npx expo start
```

For a real installable build, set `EXPO_PUBLIC_API_URL` in your EAS build
profile and run `npx eas build --platform android --profile preview`.

Testing against the deployed backend removes the same-Wi-Fi requirement in
[astraeya-mobile/README.md](astraeya-mobile/README.md) — that only applies when the
API runs on your laptop.

## The voice server

Astraeya speaks with its own voices, made on its own server: Kokoro-82M (27
voices, default **Heart**, `af_heart`) and eight Piper voices. The model files
(about 1 GB) are never committed. `render.yaml` creates the server as a
**private service** called `astraeya-voice`:

- **Plan: Standard (2 GB RAM, 1 CPU).** Kokoro needs about 1 GB once loaded.
  The free and Starter plans do not have the memory.
- **Models are downloaded during the build** by `download_models.py`, from the
  URLs in `models.json`, and each file's SHA-256 is checked. A mismatch fails
  the build instead of starting on an untested model. No disk is needed.
- **The API finds it automatically**: `render.yaml` wires `VOICE_SERVICE_URL`
  (its private address) and `VOICE_SECRET` (a generated shared secret) into
  the API. Nothing else can call it.
- **If it is down, chat is unaffected.** The web app falls back to the
  browser's own voice and shows a short notice.

How speech stays continuous: replies are cut into short pieces at punctuation,
the voice server makes up to four pieces at once (one per CPU core), and the
browser plays them in order while the next ones are being made. The live-mode
greeting and repeated phrases are cached, so they play at once.

**Heart needs real compute to be instant.** Measured on a 4-core 1.7 GHz
laptop: one second of Heart takes about 2 seconds to make on one core, so four
cores only just keep up, and the first words of a new reply take about
1.5–3 s. A single-CPU Render plan cannot keep Heart gap-free. For instant,
gap-free speech run the voice server on a GPU, or on 8 or more fast cores.
`VOICE_KOKORO_MODEL=kokoro-v1.0.fp16.onnx` selects Kokoro's official 16-bit
build of the same voices, roughly 1.4× faster on a CPU.

### Production: the voice server on a GPU (the chosen setup)

`astraeya-voice/Dockerfile.gpu` builds the voice server for an NVIDIA GPU
(CUDA 12): GPU onnxruntime, models downloaded and checksum-checked into the
image, `VOICE_DEVICE=cuda`. Not yet tried on real GPU hardware; the start-up
log names the provider in use (`CUDAExecutionProvider` means the GPU is
working, `CPUExecutionProvider` means it fell back).

1. Build and push the image, then run it on a GPU host (RunPod, Modal, or
   any CUDA 12 machine) with `--gpus all`, port 5005, and a long random
   `VOICE_SECRET`. Serve it over HTTPS.
2. On the Render API service, set `VOICE_SERVICE_URL` to that HTTPS address
   and `VOICE_SECRET` to the same secret. Remove the `astraeya-voice`
   private service from `render.yaml` (or leave it suspended as a backup).
3. Check: `GET /health` on the voice host, then read a reply aloud. On a GPU,
   first audio should arrive in well under a second.

Keep at least one GPU instance always on: a cold start reloads the models
and takes several seconds, which is exactly the delay this setup removes.

## Local development

Four terminals, or three if you skip mobile.

```bash
# 1. Postgres — create the database once
createdb astraeya

# 2. Backend
cd astraeya-api
npm install
cp .env.example .env       # set DATABASE_URL, JWT_SECRET, ANTHROPIC_API_KEY
npm run dev                # http://localhost:4000, migrates on boot

# 3. Frontend
cd astraeya-web
npm install
cp .env.example .env.local # set NEXTAUTH_SECRET
npm run dev                # http://localhost:3000

# 4. Voice server (optional: without it, read-aloud uses the browser's voice)
cd astraeya-voice
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # bin/python on macOS/Linux
.venv/Scripts/python download_models.py                   # ~1 GB into ./models, once
.venv/Scripts/python server.py                            # http://127.0.0.1:5005
```

If you already have the `voices/` folder, skip the download: the server uses
`../voices` when `VOICE_MODELS_DIR` is not set.

`JWT_SECRET` must be at least 32 characters or the API refuses to start — an
intentional guard, since a short signing secret is a real vulnerability rather
than a style preference.

## Environment variables in one place

**astraeya-api (Render)**

| Variable | Required | Notes |
| --- | --- | --- |
| `DATABASE_URL` | yes | Wired by `render.yaml` |
| `JWT_SECRET` | yes | ≥32 chars; generated by Render |
| `ANTHROPIC_API_KEY` | for chat | Without it `/chat` returns 503 |
| `CORS_ORIGINS` | yes | Comma-separated; your Vercel URL |
| `ANTHROPIC_MODEL` | no | Defaults to `claude-sonnet-5-5` |
| `JWT_EXPIRES_IN` | no | Defaults to `30d` |
| `PORT` | no | Render sets this |
| `FAL_KEY` | for images and video | Without it, only slideshow videos can be made |
| `PUBLIC_API_URL` | no | For the "video ready" webhook; polling works without it |
| `VOICE_SERVICE_URL` | no | Wired by `render.yaml`; defaults to `http://127.0.0.1:5005` |
| `VOICE_SECRET` | no | Wired by `render.yaml`; must match the voice server's |

**astraeya-voice (Render private service)**

| Variable | Required | Notes |
| --- | --- | --- |
| `VOICE_SECRET` | yes on Render | Generated by `render.yaml`; requests without it are refused |
| `VOICE_MODELS_DIR` | no | `./models` on Render; `../voices` locally by default |
| `VOICE_THREADS` | no | CPU threads per sentence; `1` on Standard |
| `VOICE_WORKERS` | no | Pieces made at once; defaults to the number of CPU cores |
| `VOICE_KOKORO_MODEL` | no | `kokoro-v1.0.onnx` (default) or `kokoro-v1.0.fp16.onnx` (faster on CPU) |
| `VOICE_DEVICE` | no | `cpu` (default) or `cuda` on a GPU host |
| `VOICE_PRELOAD` | no | Piper voices to load at start-up (none by default) |
| `HOST` / `PORT` | no | `0.0.0.0` on Render, which sets `PORT` |

**astraeya-web (Vercel)**

| Variable | Required | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_API_URL` | yes | Build-time; browser-visible |
| `NEXTAUTH_SECRET` | yes | Encrypts the session cookie |
| `NEXTAUTH_URL` | yes | Must match the deployed URL exactly |

**astraeya-mobile (Expo/EAS)**

| Variable | Required | Notes |
| --- | --- | --- |
| `EXPO_PUBLIC_API_URL` | yes in production | Falls back to `expo.extra.apiUrl` in `app.json` |

## Secrets

This repository is public. `.env` is gitignored at the root and must stay that
way — real values belong only in the Render, Vercel, and EAS dashboards. If a
key ever lands in a commit, rotate it at the provider; deleting the commit is
not enough, because the value is already published.

The frontend deliberately holds no API key. Anything prefixed `NEXT_PUBLIC_` is
readable by anyone who opens devtools, which is exactly why the Anthropic key
lives on the backend and never leaves it.

## Known gaps

Honest list of what is wired but not finished:

- **Web search** — the toggle exists and the plumbing is real, but no search
  provider is connected. Turning it on tells Claude to answer from training
  knowledge and say so, rather than inventing sources.
- **Document attachments** — images are analysed; PDFs and text files are
  stored and named but their contents aren't read yet. The chat says so
  explicitly instead of pretending otherwise.
- **Attachment storage** — neither Render nor Vercel has a persistent disk, so
  images are kept in Postgres as data URLs, capped at 1.5 MB. That is fine for
  modest use and wrong at scale; object storage (S3/R2) is the real fix.
- **Password changes and account deletion** — not implemented; the Settings
  page says so.
- **Mobile** — login, register, and chat only. No streaming (the phone gets the
  whole reply at once), no history list wired to the UI yet.
